# canonmark 路线图

结论:canonmark 分 8 个阶段(P0–P7)。核心地基是 P1(抽取参数化)+ P3(自审反馈链路)。**P0–P5 已完成并经独立验收 ACCEPT;P6(读取接线)已实现,首轮独立验收 REJECT、修复后复验判定 ACCEPT(必办项已并入 commit 6e21f78);当前处于审读修复与发布前置,acceptance 的 A17/A18 是否置 PASS 待用户拍板。** 逐项状态见 [tasks/README.md](./tasks/README.md)。

## 这个项目是什么(一句话)

把 agong_server 内部已验证的文档治理能力,抽取为一个独立、可配置的开源工具,目标三件套:① 给文档头部贴机器可校验的「权威标签」,裁决 AI agent 该信哪篇文档;② **让 AI 读任何文档都先读标签、再决定读不读正文**(protocol §3 五步判定,`canon_read` 把这一步变成机制——作废文档不给正文,只给去处);③ 用 CI 门禁保证标签不腐烂。

## 为什么做成独立仓(不在 agong 内部改)

独立仓自动绕开了 agong 内部两笔最麻烦的债:「合并到 master」和「agong CLAUDE.md 与规范打架」都不再阻塞第一版。agong_server 未来作为 canonmark 的第一个使用者接入即可。第一版只需证明:一个从 agong 抽取、去公司化的工具,能在任意项目上按配置运行。

## 阶段

### P0 奠基
产物:项目骨架、权威文档结构、协议规范初稿。出口:文档结构齐全,且能被 canonmark 自己的规范识别。

### P1 抽取参数化(地基核心)
把 agong `docs-audit.py`(1441 行)抽取到 `src/canonmark/`,项目特有硬编码抽到 `canonmark.toml`,加 `--config`;**默认值 = agong 现值(P1 时点;P5 起有意清空项目特有清单类默认,见 P5 节与 `src/canonmark/config.py` 模块 docstring)**,迁移的 42 个单测**断言零改动**全绿。(措辞须精确:断言文本确实一字未改,但调用侧有改动——迁移用例中若干处显式传入 strict 配置,且 P5 的对称性检查是破坏性变更,有一个 fixture 因此被迫修正。完整口径见 [acceptance.md](acceptance.md) 的 A1。)
必修(对抗核验坐实,不做就是半拉子):① 必须参数化最大的 `audit_v5` frontmatter 主体(L909–1139);② `status`/`authority` 词汇表定性为「治理模型固定词汇」而非项目品牌,不当可换配置暴露;③ 补 `trigger_paths`/`auditor_home` 等跨模块字段;④ 补 L471 的 docs 根字面量。
出口:`canon audit` 能在带自定义配置的项目上正确运行;42 单测全绿。

### P2 只抽通用件(擦干净)
抽取时就排除不可移植件:`gen_diagrams`(macOS 字体依赖)、task-packet lint(绑内部共识)、java hook(死代码)。新仓从第一天就干净。
出口:`src/` 无 agong 专属依赖;`pip install` 后纯标准库 + 可选 PyYAML 即可跑。

### P3 自审反馈链路(dogfood,《系统之美》核心)
canonmark 用自己的 `canon audit` 审自己的 `docs/`;接 pre-commit + GitHub Action;42 单测建独立 CI job(与文档提交解耦)。形成「文档变脏 → 自动检测 → 挡住」的负反馈回路——用最少机制,让系统自己审自己。
出口:本地提交和 CI 两条路各真跑绿一次;`canon audit docs/` 对自身全 PASS。

### P4 验收(用证据证明)
12 文件 fixture 双向 oracle(该报的精确报中 / 修好后 exit 0);同一 fixture 两份配置翻转治理词汇表(实际验的是 `allowed_statuses`,不是命名正则——原措辞「命名口径」与实际验收内容不符,已更正),证明「改配置不改代码就能换项目」;独立 subagent 验收,实现者不得自评 PASS。
出口:acceptance.md 全绿,证据齐全。

### P5 防腐烂检查组(回应「人会遗忘」)

**本阶段第一项是 T15 渐进采用,且必须排在 T10–T12 之前——顺序不可颠倒。**

T15(已完成)的一句话原则:**没做的事不罚,做错的事才罚。** 起因是实测:把 canonmark 装到一个典型存量老项目(4 篇文档、零 frontmatter)上,当时的 5 个门里 3 个 FAIL、退出码 1,接上 pre-commit 就直接卡死提交——工具在它最该被采用的场景里最不可用。做法是新增 `adoption_mode`(`gradual` 默认 / `strict`,见 `src/canonmark/config.py`):「从未贴过标签」降级为提示,只打印不判失败、不影响退出码(`GateResult.notice`,见 `src/canonmark/audit.py`);「已经贴了标签却写错」在任何模式下照旧判失败。同时把 `required_key_documents` 的内置默认值清空——「哪些文档必须存在」天生项目特有,给任何具体默认值都会让陌生项目一装上就报「固定关键文档不存在」。canonmark 自己已完成治理,仓库根 `canonmark.toml` 设 `adoption_mode = "strict"`(dogfood)。

**gradual 覆盖的范围(经独立验收扩展)**:首轮只降级了 V4/V5/V9 的「缺 frontmatter / 缺 README / 缺总导航」,验收用四种存量项目形态实测,发现另外三处照旧把人打红——① V9 的**漏链**检查与 V4 直接打架:V4 刚说「这个目录的 README 可以先不建」,V9 却要求总导航必须链接那个还不存在的文件,于是「有一个不完整的索引」这一存量项目的典型形态仍然 FAIL;② V2 目录命名:存量的 `API_Reference`、`user_guide` 是既成事实,不是这次做错的事,改名要连带改掉所有指向它的链接;③ V10 坏链:历史坏链不是这次治理造成的。现已统一口径——这三处在 gradual 下同样降级为提示,其中 V10 保留一条边界:**贴过标签的文档仍要为自己的链接负责**(与 V5 同一口径)。取舍要说清楚:V10 降级意味着 gradual 下断链检查基本让位,这是有意的——canonmark 的核心价值是文档时效性治理,拿一项附带检查拦住核心价值的采用是本末倒置,何况提示仍在,用户看得到。

**为什么必须排在 T10 之前:T10 是把要求提得更严,而实测证明存量项目连当前这一档都还过不去。** T10 要求 A 声称被 B 取代时 B 也得声明取代 A;可现状是,用户给旧文档贴一张「我作废了,去看 v2」的标签——这是收益最高、最该做的第一步——工具就会因为 v2 还没贴标签而判 FAIL,把他按进连锁治理。这是个传染陷阱:治理一篇的代价是被迫治理它指向的每一篇。先做 T10 再补渐进采用,等于先挖深坑再回填——T10 的判定逻辑要按新语义整个重写一遍。

标签本身会腐烂,而腐烂靠人记性防不住,只能靠机器发现。五类检查:
① **反向指针不对称** → 判失败。A 声称被 B 取代、B 未声明取代 A 即报错。**已实现**(T10,并入 V5,与既有的替代链环检测同族)。两处语义边界:`status: current` 却声明被取代时已判矛盾,替代链成环时「让对方认领本文档」会把环缠得更紧——两种情况都跳过对称性检查,交给各自的专属报错,避免给出会把事情弄糟的修复建议。
② `last_reviewed` 超期 → **仅提示,绝不判失败**。时间触发的失败会造成「某天全库突然变红而当天无人改动」,团队的第一反应是关闭整个门禁,与目的相反。**已实现**(T11,V11 门;阈值 `last_reviewed_max_age_days` 默认 180 天)。
③ 孤儿文档(无任何导航链接指向)→ 提示。**已实现**(T11,V11 门)。四类豁免:README 自身、docs 根下文档、所在目录还没有 README 时(否则同一件事对该目录每篇文档各说一遍,V4 已提示过一次)、已作废文档(它们本就不该被导航链接,劝人加进 README 等于劝人去踩 ⑤ 那个错);未纳入治理的文档不在本门范围内——没贴标签的文档谈不上「该被导航到」。
④ 新增文档疑似取代旧文档而旧文档未声明 → 提交时提示。**未实现,且本阶段不做。** 理由:它需要比对 git diff 中的新增文件与既有文档的相似度,而 `canon audit` 检查的是工作区快照,拿不到 diff 上下文——这属于 pre-commit hook 层而非审计层。加之它自身定位就是「无法确定、只提示」,一个不可靠的启发式提示,价值低于把它做对的复杂度。验收矩阵中本就没有对应验收项(A13–A16 覆盖 ①②③⑤),此处如实记录取舍而非假装完成。
⑤ README 文件清单与文档标签互检(见 protocol §7.6)→ 判失败。**已实现**(T12,V11 门):README 把一篇文档列为可读入口、而该文档自称 `superseded`/`archive` 时报错——导航过期藏不住,标签错误也藏不住。
出口:每类检查有 fixture 覆盖 + acceptance 对应验收项;独立 subagent 验收 ACCEPT。

**当前状态:①②③⑤ 已实现并有测试覆盖,④ 如上说明不做;独立验收判定 ACCEPT。** 过程值得记录:前三轮均判 REJECT——第一轮查出 7 个问题(其中最严重的一条是 P5 无声打破了两个已 PASS 的验收项,因为那两项当时不被任何测试引用),第二、三轮代码侧逐步通过而卡在文档口径,直到修法从「改数字」升级为「不写数字 + 让机器守」才通过。**具体计数一律以命令为准,不在本文件复制**(`pytest tests/ -q`、`canon audit docs/ --config canonmark.toml`),逐项状态见 [acceptance.md](acceptance.md)、[tasks/README.md](tasks/README.md)。

这条「不复制计数」的规矩是被自己反复绊倒后加的,四种栽法各不相同:本节曾写死一个用例数并在同一天更新 `last_reviewed`,而当天实际数字早已不同;改正时又在验收矩阵里写死了两个新的错数;接着是在陈述这条教训的句子里,顺手又写死了一个当天就作废的计数;最后一次最隐蔽——改一处测试的写法,把另一处文档里手抄的数字弄失真了,改动与失真根本不在同一个文件。**在一个专门防文档腐烂的项目里,手抄一个会变的数字就是在制造腐烂**——而且写的人每次都确信自己这回是对的。所以规矩不是「写数字时小心点」,是**根本不写**:要么由命令现场产出,要么改写成不随增删失真的性质陈述(「全绿」而不是「N 个用例全绿」)。

### P6 文档发现与读取接线(主角是 `canon_read`)
把「只读头部」从一句请求变成一套机制。依据 protocol §7:
- `canon_read` 行为契约实现(§7.4):作废文档**不返回正文**,只返回状态与替代目标。
- `canon index`(§7.5):紧凑输出 + 过滤能力;**不得**写成「每次先跑」的必经路径。
- MCP server:暴露上述两个能力,使其出现在消费者的工具面而非仅存在于文档约定。
- `canon init` 生成 MCP 配置片段与宿主指令话术(§7.7 的正确版本)。
出口:**对照实验**证明消费者读到作废文档时被拦截并改读替代目标——可复现的实验,不接受「应该会生效」这类判断。

**实现状态:T13/T14 已实现**(`canon read` / `canon index` / `canon mcp` / `canon init --print-mcp`);首轮独立验收判定 REJECT(9 问题),修复后复验判定 ACCEPT,两项必办已完成并入 commit 6e21f78。acceptance 的 A17/A18 是否据此置 PASS 待用户拍板,拍板前维持 INSUFFICIENT_EVIDENCE。

**对照实验的结论与预期不同,记在这里而不是藏进附录**:四组实测**没有任何一组答错**。无标签的两组都靠内容线索推理出了正确方向,但都明确标注低置信度、要求人拍板;有标签的两组直接确定判定。**所以标签的价值成立,但表现方式是「置信度与是否需要人介入」,不是「答对答错」**——真实成本不是 AI 答错,而是每次都要人来拍板,而这个项目的前提正是没人有空拍板。

**同时必须承认:`canon_read` 相对「只贴标签」的增量收益,本实验没能证明**——A 组不用工具也答对了。夹具只有 7 篇文档、旧文档不过几百字节,读进去几乎不要钱,而真实项目里 AI 不会通读 docs、设计文档动辄几十 KB。可量化的那部分是上下文开销:直接读进上下文的是作废文档的全长,而 `canon_read` 给出的是固定几行,**且输出长度不随文档变长而增长**(有测试守住)。真实设计文档动辄几十 KB,差距是两个数量级。此处不写具体字节数——理由同本节末尾那条规矩,另见 acceptance.md 的说明。至于省下的上下文能否换来更好的答案,需要重做实验。完整记录与设计缺陷自陈见 [acceptance.md](acceptance.md) 的「A19 对照实验记录」。

## 命名裁决(已定,来自 agent_ 前缀冲突核验)

- 默认规范:kebab-case、禁 `agent_` 前缀、ASCII 文件名——作为 canonmark 默认配置。
- agong 的 `agent_` + 中文命名是「使用者的作用域例外」,留在 agong 自己的配置里,不进 canonmark 默认。
- canonmark 自己的文档遵守默认(禁 `agent_`)——这就是最强的 dogfood 证据。

## 依赖顺序(对抗核验给定,勿按直觉)

P0 → P1(先建 config/loader,含 audit_v5 主体)→ P2(抽取即过滤)→ P3(自审 + CI)→ P4(验收)→ **P5(防腐烂)→ P6(读取接线)** → P7(发布)。

**P5 必须早于 P6,不可颠倒**:P6 让消费者依据标签跳过全文,而这个动作的全部价值建立在标签可信之上。标签仍会腐烂时先做 P6,等于在流沙上盖楼——消费者会据此跳过真正该读的文档,比不做更危险。

铁律:「发布」永远最后,且永不自动执行。
