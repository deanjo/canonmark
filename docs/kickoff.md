# canonmark 开工卡

> 本卡是编排纪律的唯一权威版本。后续任何「回顾纪律」的需求,读本文件回答,不重新生成。

【目标】把 agong_server 内部已验证的文档治理能力抽取为独立开源工具 canonmark——一个「裁决 AI 该信哪篇文档」的可配置审计工具。完整目标三件套:给关键文档贴权威标签(frontmatter);**让 AI 读任何文档都先读头部标签、再决定读不读正文**(protocol §3 五步判定,`canon_read` 落地为机制);用审计门禁保证标签不腐烂。(第二条系 2026-07-29 应用户要求明写进本卡——此前仅存在于 protocol §3,目标句漏记导致历次总结丢失这条。)完成地基(抽取参数化 + 去公司化 + 自审反馈链路),用证据证明可跨项目运行。首轮委托划定的不做清单:GitHub 远程公开发布(留用户拍板)、agong_server 侧接入改造、推广到其他公司仓、独立 spec 站点、prose / 格式 lint、外链检查。

**范围更正(2026-07-27)**:上面这份清单原本还含「MCP server」,但 P6 已按 roadmap 与用户放行交付了 `canon mcp`——**文档与已发生的事实冲突时以事实为准,文档随之修正**(protocol §5.4)。留着那一句会让这份 `contract-current` 文档明文禁止一件已经做完的事,正是 canonmark 要消灭的缺陷形态。其余各项仍然有效。

【纪律】任务复杂度达到「多文件 / 多步骤 / 可拆分」时,善用多 subagent 提效,前提是有高价值收益才并行。主 agent 保持上下文干净,只负责:协同、拆分任务、维护权威文档(docs/roadmap.md)、调度实现 agent 与验收 subagent、汇总证据、判断是否进入下一轮。实现 subagent 模型:会话默认。验收必须独立:实现者不得自评 PASS。长期状态必须落到 docs/tasks/ 与 docs/progress.md,不能只依赖聊天上下文。

【验收矩阵】所有目标量化:影响范围 / 验收项 / 测试命令 / 通过条件 / 失败条件 / 证据路径 / 未验证范围(见 acceptance.md)。判定五态:PASS / FAIL / BLOCKED / INSUFFICIENT_EVIDENCE / NOT_APPLICABLE。禁止「效果更好」这类无法验收的目标。runtime 可见的改动,完成 = 真实运行通过且证据齐全(真实命令输出、退出码、测试计数;仅编译过 / 单测绿不足以覆盖跨项目运行的证明)。

【红线】出现以下情况必须停下挂起,等用户确认:
1) 删除任何验证资产 / 索引 / 数据(删除类操作一律留到用户在场);
2) 任务书未列明的新功能(不自行实现,挂起);
3) 不可逆操作:GitHub 远程仓库创建 / 推送、发布、修改 agong_server 仓库文件、生产与配置写入、花钱类操作。

【循环节奏】问题定义 → 设计文档 → 执行计划 → AI 实现 → 自动化验证 → subagent 独立验收 → 反馈修复 → 更新文档与证据 → 再验收,直到验收矩阵全绿。系统不是越复杂越好,而是越简洁、越实用、越鲁棒越好;用最少必要机制。最大化 AI 工作量,人只做必要决策、不手写代码、不手动做测试验证。本次进入自主推进模式(用户离线委托),触碰红线立即挂起。

【心跳】每完成一个阶段,向 docs/progress.md 追加一行(时间 + 阶段 + 状态 + 下一步),用户看文件,不等催问。
