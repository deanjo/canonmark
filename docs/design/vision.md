# canonmark 愿景:让 AI agent 知道该信哪篇文档

结论先行:AI coding agent(Claude Code / Cursor / Copilot)读项目 `docs/` 时,会被过期或互相矛盾的文档误导,进而写出错代码。现有工具栈里,`markdownlint` 管格式、`Vale` 管措辞、`lychee` 管断链,却没有任何一层管「这篇文档还算不算数」。canonmark 补的正是这一层——AI 上下文标准栈里缺失的「文档生命周期层」。一句话边界:**AGENTS.md 告诉 agent 怎么干活,canonmark 告诉 agent 该信哪篇文档。**

## 一、要解决的问题:文档会腐烂,而 agent 不知道

agent 把 `docs/` 当权威上下文读,但文档会随时间腐烂:被新版取代、被删接口留在旧文里、两份规范互相打架。人类读者靠经验和上下文能绕过这些坑,agent 不能——它把每一句都当成还生效的事实。两个真实例子:

### 例子①:两份硬约束互相打架,305 个文件卡在中间,且无机制发现

在 `agong_server` 仓(canonmark 未来的第一个使用者)里,存在一对无法同时满足的硬约束:

- `agong_server/CLAUDE.md:84` 规定:`docs/deep_search6.0/` 下所有 Markdown 文档**必须**以 `agent_` 前缀开头。
- `agong_server/docs/engineering/agong-docs-standard.md:106` 规定:新建文档**禁止**以 `agent_` 前缀开头(标注为「硬约束」)。

两份文档都自称权威,结论完全相反。夹在中间的是 `docs/deep_search6.0/` 下 **305 个** `agent_` 前缀文件(实测:`find docs/deep_search6.0 -name 'agent_*.md' | wc -l` = 305,占该目录 359 个 md 文件的 85%)。关键不在于「谁对」——人可以事后裁决说「这是使用者的作用域例外」——而在于:**在裁决发生之前,没有任何机制会发现这对约束互相矛盾。** agent 读到哪份就信哪份,取决于它先命中哪个文件。canonmark 的元数据契约让「谁取代谁、谁在什么场景说了算」变成机器可校验的字段,矛盾在写入时就会被审计器挡住,而不是等某个 agent 写错代码后才暴露。

### 例子②:agent 自信调用一个早已删除的接口

一个接口在代码里已经删除,但一份旧设计文档里还写着它的签名和用法,且这份旧文档没有任何「我已过期」的标记。agent 读到它时,没有任何信号提示「这段不再生效」,于是自信地生成调用该接口的代码——编译不过,或更糟,调到了一个语义已变的同名接口。问题的根不是文档写错了(它在当时是对的),而是**没有一层元数据声明「这篇已被取代,别把正文当现行事实」**。canonmark 的 `status: superseded` + `superseded_by` 就是这层声明:agent 判定协议第一步就跟随指针改读现行文档,旧正文默认不加载。

## 二、价值:补上 AI 上下文标准栈缺失的一层

把文档当 AI 上下文来治理,今天已经有成熟工具,但它们各管一段,唯独漏了「权威与生命周期」:

| 工具 | 它管什么 | 它不管什么 |
|---|---|---|
| `markdownlint` | 格式(标题层级、列表缩进、行长) | 这篇文档还算不算数 |
| `Vale` | 措辞(术语、语气、风格一致性) | 这篇文档还算不算数 |
| `lychee` | 链接可达性(断链检测) | 这篇文档还算不算数 |
| **canonmark** | **文档权威与生命周期(谁现行、谁被取代、谁在什么场景说了算)** | 格式 / 措辞 / 断链(交给上面三者) |

canonmark 不替代任何一个,而是补齐它们共同的盲区。它把每篇关键文档头部的「权威标签」(8 字段 frontmatter,详见 [protocol.md](./protocol.md))定为机器可校验的契约:哪篇现行、哪篇被取代、冲突时谁赢——并让审计器在标签腐烂时挡住构建。

## 三、为什么这是真问题(证据)

- **过期文档是 LLM 上下文里最强的干扰项。** Chroma 的 Context Rot 研究指出,随上下文增长,模型对内容的可靠利用会下降,而其中过期 / 相互矛盾的片段是最典型的性能杀手——agent 会被看起来权威、实则失效的段落带偏。
- **文档天生会腐烂。** 有研究统计,约 50% 的上下文 / 文档文件在创建后**从不更新**。这意味着任意时刻,一个项目 `docs/` 里都有相当比例的文件正在悄悄偏离现状,而没有任何标记提示 agent 这一点。

这两点合在一起解释了为什么「格式 / 措辞 / 断链」全绿的文档库,依然能让 agent 写出错代码:所有现有闸门都通过了,唯独没有闸门问一句「这篇还算不算数」。

## 四、差异化与诚实边界

**差异化。** 2026 上半年,同一方向正在涌现一批早期项目,各自形态不同:

- `ejklock/living-docs-skill`——做成 agent skill;
- `sandyeveliz/docwarden`——做成 CLI;
- `CortaLabs/scribe_mcp`——做成 MCP server。

它们大多聚焦「新鲜度检测」(这篇文档多久没更新了 / 是否偏离代码)。canonmark 的差异化不在新鲜度,而在**权威裁决(谁说了算)**:当两篇文档给出互斥结论时,元数据能机械判定谁现行、谁被取代、谁在当前任务里能主导——这是新鲜度检测答不了的问题(例子①里两份文档可能都很「新鲜」,冲突照样存在)。第二个差异化是**对中文文档库的一等公民支持**:字段值、审计报告、判定协议原生支持中文场景,而非把 CJK 当边角料。

**诚实边界(未验证范围)。**

- 上述痛点的**量级尚未经大样本调查证实**。例子①②是实测锚定的真实个案,但「有多少项目、多大比例受此困扰」没有系统性数据支撑,不应据此夸大普遍性。
- Chroma Context Rot、「约 50% 文件从不更新」这两条外部证据由本项目引用而非独立复现;引用它们是为说明方向合理,不构成对 canonmark 具体收益的量化承诺。
- 同类早期项目仍在快速演化,上面的形态归类是当前时点的观察,可能随其迭代而变化。

canonmark 第一版只求证明一件事:一个从 `agong_server` 抽取、去公司化的工具,能在任意项目上按配置运行,把「文档该信哪篇」变成一道机器可校验的门禁。收益的量化证明留给验收(见 [acceptance.md](../acceptance.md)),不在本文件承诺。
